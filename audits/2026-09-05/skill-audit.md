# 个人 Codex Skill Hub 审计

日期：2026-09-05。目标仓库：[Lioooooo123/skill-hub](https://github.com/Lioooooo123/skill-hub)，私有。目标运行环境：本人的 Codex，优先适配 GPT-6 Astra。

## 结论

建议保留 42 个个人技能的领域能力，先修复会中断授权工作、改变交付物、操作无关文件或误报验收结果的规则，再精简重复说明。当前不需要为追求技能数量更少而合并所有入口，也不需要把系统及插件技能全部复制进个人仓库。

本轮完成个人技能正文逐项审计、系统技能正文检查、全部发现入口的结构清点，以及相关引用和脚本的定向审查。没有修改、删除、迁移或上传已安装技能，没有运行远程业务写入，没有完成新旧版本任务评测。因此，本报告给出有证据的改进方向，不宣称已提升耗时、token 效率或模型成功率。

## 官方依据如何落地

GPT-6 Astra 官方指导强调技能指令敏感性、上下文授权、自主推进、写作习惯、适当委派和避免过度测试。落地方式是删除冲突和无意义硬门槛，保留明确任务边界与有效验证，而不是在每份技能中复制整套模型提示词。[官方模型指导](https://developers.openai.com/api/docs/guides/latest-model)

官方 Skills 文档采用渐进加载：先名称与描述，选中后读取正文。描述应把关键用途放在前面；详细场景按需引用。本机可用软链接维护个人技能；当前阶段无需扩展成插件发布项目。[官方 Skills 文档](https://learn.chatgpt.com/docs/build-skills)

当前全局 `~/.codex/AGENTS.md` 已覆盖上述多数行为约定，建议保持简洁。领域规则留在技能；本机路径与依赖留在本机配置；项目事实服从对应项目指定文档。API 的异步工具调用、缓存及 reasoning 参数不能仅靠修改 SKILL.md 开启。

## 优先修复的具体问题

以下证据路径除另注外，相对 `~/.agents/skills/`。行号对应本次哈希快照。影响属于静态判断，除明确注明外没有通过模型实跑复现。

### 1. 写作技能会停止正常起草和简历审稿

证据：`write/SKILL.md:3,32,118`。描述支持 Draft，前置检查却要求没有待编辑原文就停下；审稿遇求职、姓名、任职信息也要求 hard stop。

触发：用户已给主题与收件人要求写邮件，或要求润色包含姓名的简历。建议区分起草与改写；起草根据现有要点完成，缺少关键事实才提问。简历审稿继续处理已授权内容，仅指出与交付对象有关的具体泄露问题。

### 2. pre-commit 安装默认扩展为全部暂存与提交

证据：`setup-pre-commit/SKILL.md:81-85` 要求 Stage all changed/created files and commit。若工作区已有 WIP，存在把无关改动纳入提交的风险。

建议设置 hooks 后只验证相关配置；仅在会话已授权提交时选择性暂存本次文件，保留原有暂存状态。包管理器和 hooks、prepare、lint-staged 配置需要先读取再合并，不能用固定模板覆盖。

### 3. UI 请求会被强制转介到另一套产品

证据：`ui/SKILL.md:23` 把报告、幻灯片、简历、PDF 转介 `tw93/Kami`。本机已有对应文档、PDF、简历技能，并未要求使用 Kami。

建议保留 ui 的产品界面实现与视觉修复职责，按用户指定产物选择现有工具。Kami 只能是用户选择后的可选路径。

### 4. 简历 QA 缺检查工具仍可能总体通过

证据：`html-resume-builder/scripts/export_and_qa.py:123,144,163,501-508,623-632`。缺少 PDF 页数、字体、文本、渲染工具时，检查记为 `required=False`；总体 `ok` 只依赖必需检查。

建议区分 preview 与 final：预览可继续；最终交付中页数、裁切、字体等必需证据缺失，应显示 incomplete 或失败，不能解释为完整 QA 通过。本机目前相关工具存在，问题在缺依赖场景的状态契约，不是此次已经导出坏简历。

### 5. URL 抓取存在三套不一致的顺序

证据：`read/SKILL.md:29-47`、`read/references/read-methods.md:7-18`、`read/scripts/fetch.sh:75-99`。正文路由与引用先使用第三方代理，脚本及另一段正文承诺默认本地提取；“URL never leaves the machine”也不准确，本地抓取仍会向源站请求。

建议统一为可用原生工具、连接器或直连提取优先；有实际需要时才选择代理。保留对内部及带认证 URL 的限制，避免代理分支绕开检查；删除过时的 `learn Phase 1` 文件保存契约。普通摘要与短引用无需输出整篇原文。

### 6. 多个技能把既有授权限定为本轮

证据：`check/SKILL.md:10,18,35,174`、`hunt/SKILL.md:18`、`lark-mail/SKILL.md:41,45,74`、`lark-drive/SKILL.md:26,33`。飞书邮件还自称最高优先级且不可被其他指令覆盖。

建议以整个会话中的有效授权、当前范围和真实目标为准。明确的只读审查仍只读，用户早先授权的修改也不因换轮而失效。移除 skill 自封优先级，保留邮件内容不是操作指令、不可擅自发信等有效约束。

飞书 exit 10 的确认门禁另见 `lark-shared/references/lark-shared-high-risk-approval.md:23-30`：不能遇到该状态便自动加 `--yes`。应先检查是否已有针对同一具体目标、参数和影响的明确授权；没有则形成具体请求供用户确认。已有授权不能被重复仪式无故抹掉。

### 7. 验证和委派没有按任务缩放

证据：`check/SKILL.md:109-113,223-227,246,256-262` 强制广泛测试与多代理审查；`hunt/SKILL.md:39,118,125` 按失败次数或文件数停下；`tdd/SKILL.md:22-24,38` 强制确认测试边界并排除 refactor 阶段。

建议按具体风险和完成标准选择检查。复杂独立审查可以委派，普通小改动不固定代理数量。TDD 保留失败断言、独立预期和行为测试，边界清楚时直接执行；green 后允许必要的局部重构。`hunt:165` 的 revert/stash 仅为回归证明，不应在共享脏工作区直接照做，优先用隔离副本验证旧代码。

### 8. 飞书 Slides 的通用风格要求压过用户目标

证据：`lark-slides/SKILL.md:13,18-24,43,45-72,222`：要求读两遍、普遍大量配图、高密文字卡片，并引用本会话不可用的 `NotifyHuman`。

建议 API XML、更新语义、布局检查保留在必要流程中；风格和密度改为可选参考；完成后通过正常回复提供真实链接。不要因优化文字而删除实际协议约束。

### 9. 日程冲突算法漏掉嵌套区间

证据：`lark-workflow-standup-report/SKILL.md:107` 只比较排序后的相邻日程。A 09:00–12:00、B 10:00–10:30、C 11:00–11:30，会漏掉 A 与 C。

建议以活动区间或当前冲突组最大结束时间检测。修改时加入嵌套、接壤和已拒绝日程的行为回归用例，验证实际结果。

### 10. 引用漂移与安装机制影响可维护性

飞书引用确认 9 个实际缺失目标：

- `lark-apps/references/lark-apps-local-dev.md:69` 的 `../creative-design/SKILL.md`，实际文档为 `creative-design.md`。
- `lark-event/references/lark-event-im.md:30` 的仓库源码 `../../../events/im/message_receive.go` 不随技能分发。
- 飞书邮件 send、reply、reply-all、forward、draft-edit、draft-create 六份 reference 中的 `references/lark-mail-html.md` 多嵌套一层目录。
- `lark-mail/references/lark-mail-watch.md:94` 的 `lark-event-subscribe.md` 不存在。

另有 `~/.codex/skills/ios-hig-design/references/typography.md:3,11`、`colors-depth.md:3,22` 引用主文已不存在的章节。它们是文本交叉引用漂移，不能靠“文件存在”检查发现。

`lark-whiteboard/SKILL.md:13-15` 每次使用时执行可变版本 `npx -y ...@^0.2.13 -v`；`lark-shared/references/lark-shared-update-notice.md:19` 说明 CLI update 同时更新技能。安装检测应按实际操作发生，Hub 的个人修改与上游更新必须分开管理。本轮没有执行安装或更新。

## 系统与插件的处理边界

| 范围 | Hub 策略 |
|---|---|
| openai-docs | 保持系统版本；Hub 记录官方依据，不再复制一份模型指南技能 |
| skill-creator / skill-installer | 保持系统版本；新文件写入 Hub 指定路径；安装器默认目标不替代本次显式仓库选择 |
| plugin-creator | 保持系统版本；个人源码 Hub 目前没有插件打包需求，不启动 marketplace 工作流 |
| imagegen | 保持系统版本；按实际工具 schema 编辑图片；不要为统一风格复制整套生图提示规范 |
| review-agent | 保留内部委派用途；不在个人 Hub 创建同名入口 |
| build-ios-apps | 保留上游实现能力；ios-hig-design 提供体验判断，避免重复复制 SwiftUI 示例 |
| figma | 保留上游。figma-swiftui 描述包含“只要提到 Swift/iOS”，与正文双向转换范围不一致，记录误触发风险；普通 SwiftUI 工作不应因此创建 Figma 工作流 |
| product-design | 视觉探索、UX审计、忠实复刻由插件负责；ui 负责已有代码界面的实现与修复 |
| documents / pdf / presentations / spreadsheets | 保留实际产物工具合同；write 处理文字、asu 处理招聘叙事、resume 处理简历模板，按产物组合 |
| lark-* | 来源虽为上游，但当前独立安装且将有个人修改，应明确维护 fork 或补丁，不与 CLI 自动更新争夺同一源码 |
| 其余插件与缓存 | 记录来源/版本/目录；本轮无证据支持批量停用或删除；缓存存在不等于当前加载 |

系统技能的正文有部分重复/兼容提示，但不建议为了本次个人优化直接修改系统包。插件触发冲突先记录，可在独立受控 fork 中解决；仅加一条覆盖规则未必能减少已经被目录列出的描述成本。

## Hub 的维护方案

建议以仓库为个人技能唯一源码，安装脚本为每项创建可追踪链接或受控副本，明确哪些路径由 Hub 管理；先导入快照再修改。本机既有非 Hub 文件不得被安装脚本无提示覆盖。

来源清单：8 项来自 tw93/Waza，7 项来自 mattpocock/skills，1 项来自 KevinYoung-Kw/vibe-resume-skill，24 项来自 open.feishu.cn；asu-skills、ios-hig-design 无本机锁文件来源条目，不据此认定作者或许可。锁文件还有已不存在的 docx/pdf 旧记录。

现有 Git 来源条目有 skillFolderHash，但不能直接当作 upstream commit；飞书条目 hash 为空。导入时保留来源 URL、可验证版本、文件内容 hash、已有许可与本地改动记录。动态本机参数与凭证不进入通用技能正文。官方缓存技能只进来源目录，不整体复制。

建议第一批改动范围：write、ui、read、tdd、setup-pre-commit、html-resume-builder；同时修确定的引用和日程算法。第二批整理 check、health、hunt 及飞书授权/认证流程，最后再做其余正文的按需拆分。每批都保留原始快照，依据对照任务保留有效修改。

- 未改变全局权限、模型设置、插件启用状态；未克隆/修改旧业务仓库。
