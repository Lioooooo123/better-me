# 有证据的审查

明确审查对象与比较基准。检查项目约定、工作区状态、完整目标 diff 及相关调用方；分支审查使用共同祖先，另看未提交改动。不要把缓存的行号或旧基准当成当前证据。

沿实际执行路径寻找可复现或可从代码证明的问题。区分此次引入的回归、既有问题与迁移遗漏；说明触发条件和影响，避免把个人风格偏好当 bug。

根据风险和交付物选检查：例如类型/构建检查、受影响测试、实际数据边界或可视状态。读取现有包管理器和命令后执行相关已授权检查；缺某项检查时如实记录，不凭空要求项目增加测试体系。

由当前 Agent 完成审查。仅当用户明确要求启动子 Agent 时才委派独立范围，说明输入、输出和完成标准；不因审查复杂或风险较高自行启动。

审查请求本身是只读；如果会话已授权修复，则先形成明确发现，再完成范围内修复。保留无关改动，验证旧代码时用隔离副本。锁文件首先检查包管理器版本和冻结安装结果，不用任意重生成的差异证明它错误。

输出按影响排序的发现，附准确位置、触发路径和修复建议。简洁说明已完成的验证及实质缺口。无有效发现就直说，不凑固定台账。

源码验证、已安装行为和发布完成分别报告；只有要求发布时才检查发布资产与安装渠道。

联动：CI 失败调查用 `gh-fix-ci`，正在进行的合并冲突用 `resolving-merge-conflicts`；根因尚不明确用 `hunt`；明确模块问题用 `codebase-design`。对方已提供可靠检查结果时复用，只有新改动或证据疑点才重跑。
