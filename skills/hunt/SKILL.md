# 故障定位

收集实际症状、预期行为、发生环境与最近变化，优先复用用户提供的日志和复现步骤。先建立最小的证据链，再修改代码。

每次探针回答一个问题：哪个边界最先偏离预期、什么输入触发、哪个假设被排除。对偶发竞争或外部服务故障，可用带时间/关联 ID 的迹象缩小范围，不强求完全确定的复现或单一根因。

失败的假设应促使重新整理证据和选择下一项有效探针，不因固定次数或文件数自动停工。只有缺少不可替代的外部信息或需要改变任务范围时才提问。

修复最接近根因的边界，检查同类调用是否受影响。保持无关行为和工作区内容；不要通过吞掉异常、跳过检查或替换真实数据让症状消失。

验证应证明原问题已解决并覆盖相关回归风险。对复发或逻辑性缺陷，优先建立能在旧代码失败的行为回归测试；用隔离副本验证旧实现，不在共享脏工作区 stash/revert。环境配置或低影响可逆问题使用与其相称的检查。

已授权修复则持续完成；仅要求解释时提供根因与建议。交付说明原因、修改、验证证据和仍未解决的限制，不把“测试通过”扩张为真实设备或生产验收。

联动：测试驱动实现可用 `tdd`；必要的模块调整用 `codebase-design`；修复后有独立风险时用 `check`，不重复已经充分的验证。
