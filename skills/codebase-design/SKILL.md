# 模块与接口设计

先理解代码当前承担的职责、调用关系和实际修改痛点。沿用项目已有 service、module、API 等术语，必要时解释它们对应的概念，不强制替换词汇。

好的边界把实现复杂度藏在小而清晰的接口后面。优先减少跨模块必须同时知道的事情，而不是增加文件、接口数量或抽象层级。

按当前需求考虑替代方案：调用方是否更简单、数据所有权是否明确、错误与生命周期由谁处理、外部依赖能否在合适边界隔离。单实现的接口在隔离或稳定契约有价值时也可以成立。

接口不仅是函数签名，还包括调用顺序、错误语义、配置、数据所有权和调用方必须知道的性能限制。评估抽象时做一个反向检查：去掉它后，复杂度会消失，还是散落到多个调用方？后者才说明它在集中承担职责。

重构前明确需保持的可观察行为，沿调用链分步迁移。旧测试只有在行为覆盖确已重复或边界不再存在时才移除，不能因为有新接口测试就整批删除。

只有多个可信方案值得独立探索时才并行设计，不规定最低 Agent 数。交付推荐边界、关键接口与迁移/验证方式；用户授权实现时完成修改。

联动：业务术语需要统一时用 `domain-modeling`；测试驱动迁移用 `tdd`；`check` 验证实际改动，不重新开一次完整设计流程。
