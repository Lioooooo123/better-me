# Git 冲突处理

先读取 `git status`、未合并路径及相关提交，确认当前在 merge 还是 rebase、目标分支和待重放提交。记录已有暂存与无关修改，不用批量 ours/theirs、reset 或 stash 清理现场。

对冲突文件查看共同基线与双方版本：`git ls-files -u` 展示冲突阶段，普通内容冲突可用 `git show :1:<path>`、`:2:<path>`、`:3:<path>`。新增/删除冲突未必有全部阶段；rebase 的 ours 通常是接收重放的基线，theirs 是正在重放的提交，不能把分支名与阶段含义想当然地对应。

从提交说明、调用方、测试与已有 PR 背景理解双方为什么修改。能兼容就保留两个意图；发生实质业务冲突时按明确合并目标处理，缺少决定依据才提问。不要凭空加入第三种行为。

逐个解决代码、重命名、修改/删除和生成文件。锁文件沿用对应包管理器与项目版本处理，先确定清单的正确合并结果，不手拼哈希或升级无关依赖。

运行冲突影响范围的构建或测试，确认无未合并条目；文本冲突标记扫描只是辅助，不能替代行为检查。只暂存本次解决的路径，避免 `git add .` 混入无关修改。若已有无关暂存内容，先确认能安全隔离；不能隔离时保留解冲突结果并说明提交缺口，不能将它们混进合并提交。

用户要求完成整个合并/变基时，在验证后提交 merge 或继续 rebase，并处理余下提交；只要求修文件或先看方案时停在对应范围。遇到无法安全判断的冲突保留可恢复现场并说明缺口；不擅自 abort，也不违背用户明确的取消要求。推送和强推需要对应授权。

联动：合并暴露的具体故障用 `hunt`，完成后有独立风险时用 `check`；复用已有验证，不重复完整审查。
