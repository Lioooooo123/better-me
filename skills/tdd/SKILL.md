# 测试驱动开发

从需求、现有公开接口和测试惯例确定行为边界，复用已确认的约定。清楚的边界直接使用；只有不同解释会导致不同产品行为时才提问。

每次选一项有意义的行为：

1. 写能识别缺失行为的测试，运行并确认它因预期原因失败，而不是环境或语法错误。
2. 写足够实现该行为的代码，运行相关测试确认通过。
3. 有必要时做保持行为的局部重构，再运行受影响检查。

预期值来自独立事实、规格或人工可核对的例子，不复刻实现来计算预期。不为内部方法名、任意文字或临时数据结构写绑定实现的断言。

优先在稳定业务边界观察结果。需要替代网络、时钟或其他外部依赖时，替代依赖边界并保留协议一致性；不要 mock 掉正在验证的业务行为。

已有 bug 用能够区分旧行为与修复行为的输入。涉及旧代码验证时用隔离副本，保护现有未提交工作。测试范围随风险缩放，避免在一个周期提前设计所有未来行为。

联动：根因不明先用 `hunt`；边界设计存在实际问题再用 `codebase-design`。通过后的独立审查可以用 `check`，但 refactor 不必等待另一项审查任务。
